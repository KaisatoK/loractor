# AGENTS.md

Role-aware log-investigation chatbot: Streamlit UI (`src/ui`) -> FastAPI backend (`src/backend/api.py`) -> LangGraph pipeline (`src/backend/pipeline/graph.py`) -> SereneDB log queries (`src/backend/db`).

## Challenge goal (build target)

One workflow — **question -> evidence -> recommendation** — for three roles: **engineer** (investigate a specific error), **team_lead** (recurring problems/patterns), **manager** (prioritize by impact). Answers stay grounded in log data, use reliable computed summaries, and are tailored per role. The source brief is `Making Sense of Logs - The Right Insights for the Right People.pdf` in the repo root (scoring: role-appropriate insight 30%, search + analytics 25%, recommendation quality 25%, execution 20%).

- Role objectives live in `src/backend/pipeline/roles.py` (`ROLE_OBJECTIVES`, answer side) and the role **playbooks** in `skills/engineer-investigation`, `skills/recurring-patterns`, `skills/risk-prioritization` (evidence side; `ROLE_SKILLS` maps role -> skill). Role names are in `src/backend/pipeline/state.py` (`RoleName`). Keep these authoritative when changing role behavior. A playbook's body is injected into the `find_evidence` prompt (`pipeline/playbooks.py`) and also served by the MCP `read_skill`, so Claude connected to the MCP server gets the same behavior.
- "Evidence" = the DB query tools in `src/backend/pipeline/tools/` + `src/backend/db/`; "recommendation" is the answer/confidence stages. Prefer computed aggregates over LLM-inferred numbers: counts, shares, trends and the priority score are computed in code or SQL, never by a model (Jev/LLMs are unreliable at counting and comparing numbers).
- Different roles must get **different evidence and next steps**, not just a different answer length: engineer = search + nearby events + isolated-or-recurring count; team lead = counts by event/component/team + trend; manager = ranked priorities from measured frequency, severity share, trend and breadth. Wording rule from the brief: count log entries, never "incidents"; search examples never establish frequency.
- Gotcha: `src/ui/roles.py` `ROLES[].description` holds generic assistant copy ("Debug code, review designs…") that does not match `ROLE_OBJECTIVES`. Don't treat it as the source of truth for role intent.

## Integrating new tools and tables (READ THIS when the MCP tools / real tables arrive)

The role behavior was built **ahead of** some tools and data. These are the explicit assumptions and placeholders; when the real thing lands, replace them — do not leave both.

**Tool-result contract** (`src/backend/pipeline/tools/envelope.py`). Every evidence tool, local or MCP, must return `{status, operation, kind, dataset, query, filters, limit, returned, total_matches, truncated, data}`; build it with `run_enveloped` (the generated local tools and MCP server tools both do, from the spec table). `kind` is one of `search | context | aggregate | trend | lookup | catalog | test`. Only `aggregate`/`trend` (and the code-derived `derived` priority table) are measured frequencies; `search`/`context`/`lookup` are examples. `collect_tool_results` copies these fields onto every `R{n}` record; a legacy envelope that lacks them yields `None` (shown as "unknown"/"not reported" in the answer), except `kind`, which falls back to `TOOL_KINDS` by tool name. `truncated` is `total_matches > returned` when the total is known, else `returned >= limit`, else `None`.

**Implemented T2/T3 tools** — `get_nearby_events_tool` and `count_by_team_tool` are
both declared with a `run` in the spec table, so every transport offers them.
`count_by_team_tool` uses the real `team_ownership` table with a corpus-and-component join, returns
measured `{dataset, team, severity, count}` rows, and keeps unmapped components
as `unowned`. Team lead and manager playbooks call it directly; the CSV remains
prompt context for naming component owners. The hypothesis-test tools remain
planned.

**Every new tool is one `ToolSpec` entry** in `src/backend/pipeline/tools/specs.py` (plus its DB function in `backend/db/` and its argument model in `tools/schemas.py`, where every parameter needs a description and every `limit` its bounds). The local tool, the pipeline's MCP wrapper, the MCP server tool, `TOOL_KINDS` and `TOOL_CATALOG` (the classifiers' catalog line is the spec's `catalog` text) are generated from it -- never write a tool out a second time (`tests/test_tool_specs.py` fails if you do). The `description` says what the tool is for, when to use it and which tool instead, what it returns, its limits and what an empty result means; it does not repeat the inputs (the parameter schema does). Mention the tool in the relevant `skills/*/SKILL.md`. For a planned tool, supply `run` and set `available=True` and drop the "NOT AVAILABLE YET" prefix of its catalog line. `get_nearby_events_tool` and `count_by_team_tool` are the worked examples (the DB functions are `db/context_query.py::get_nearby_events` and `db/count_query.py::count_by_team`; their operation labels live in `specs.py`). Then re-run `bash ./routes.sh` and `bash ./confidence.sh` (the catalog is part of both classifiers' state). Tests patch a DB function once, as `specs.<name>`, for every transport.

**Nearby events (`get_nearby_events_tool`, kind `context`).** The lines around one anchor `line_id` in record-id order (file order, and on OpenStack also time order), not a time slice: `before`/`after` 0-50, rows carry `offset` (negative before, 0 anchor, positive after). `same_entity` narrows to the anchor's `entity_id` (Pid / Node); `same_request` to its `request_id` and is refused (`unsupported_field`) where the dataset has none -- only OpenStack does. Datasets without `record_id` (`otel_s3`, `otel_slice`) are refused. An unknown anchor is an empty success with a `query_stats.notes` entry, as is an anchor with no value for the flagged field (only the anchor comes back). The nearby rows use one statement, measured ~10-50 ms on both local corpora; `same_request` also adds an exact request-context summary (row count, first/last timestamp and component count), which identifies broad periodic contexts.

**Ownership table.** `src/backend/data/team_ownership.csv` is a **fictional** `dataset,component,team` mapping (README documents it). `component` matches the corpus's `Component` column (the registry's `service` field) exactly. `backend/db/ownership.py` reads and validates it (`read_ownership_csv`) and `uv run python -m backend.db.ownership` (re)loads the `team_ownership` table (no log table is touched). When the organisers' real table arrives, replace the CSV (keep the three columns), reload it, and update the README team table. The measured CSV includes OpenStack, BGL and OTel components; unmapped components count as `unowned` (`UNOWNED_TEAM`). `count_by_team_tool` joins this table by corpus and component, and `setup.sh` loads it before the log tables.

**Datasets / tables.** Corpora are registered in `db/datasets.py` (`openstack`, `bgl`, `otel_s3`, `otel_slice`); tools take a `dataset` id, never a table name, and rows use the canonical field names (`ts`, `severity`, `service`, `message`, `entity_id`, `template`, `event_id`, `record_id`, `request_id`). The tool-result envelope's `dataset` is that id. The local corpora have no `event_id` (loghub publishes one only for its 2k samples), so recurring patterns are counted by `template`. `request_id` is declared on OpenStack only, as a code-owned expression over `ADDR` (`datasets.OPENSTACK_REQUEST_ID_EXPRESSION`: the first word when it starts with `req-`, else NULL), so it needs no reload; a code-owned expression must not contain a bare `%` (psycopg2 reads it as a placeholder in any query with parameters), hence `left("ADDR", 4) = 'req-'` rather than `LIKE`. When adding a corpus: register it, check its `severity_values` against `priority.INFO_LEVELS`/`SEVERE_LEVELS` (`test_priority_levels_cover_every_registered_dataset` enforces it) and its `Component` values against the ownership CSV.

**Verification.** After any change to the tools, prompts or skills, re-run the live DB tests (`RUN_OPENSTACK_LIVE=1`), `bash ./routes.sh`, `bash ./confidence.sh` and `bash ./worked_investigation.sh --topic "<a real recurring issue>"`, and re-read the SQL appendix by hand against direct queries.

**SereneDB operations gotchas (hit while verifying):** (1) the container's host port is not stable (`docker ps` showed 7892, then 7893 after a restart); set `SERENEDB_PORT` in `.env` to the current mapping (default 7890 is the in-container port). (2) Search is lexical (BM25) now, so the `local_ai` embedding secret only matters for the opt-in template embeddings. Never hard-code observations about one dataset (which levels exist, which pattern recurs, how long the window is) into prompts, skills, defaults or plans: the data can be anything; the agent must measure it each time.

**Bugs found only by the live run (keep their tests):** Decimal/datetime values in rows made LangChain serialize a tool result as a Python repr, so `collect_tool_results` silently dropped every search and line-id lookup (fixed by `envelope.json_safe`; regression test in `test_tool_envelope.py`); the result catalog cut cell values at 60 characters and the answer quoted a shortened hash as real (now `builders._clip` with an explicit `…[cut]` marker); the report formatter produced 4 hypotheses against a max-3 contract the prompt never stated (now in `JSON_OUTPUT_SPEC`); search applied severity only after the BM25 top-100 cut, so a severity ranked below it vanished (OpenStack 'instance' at ERROR returned 0 of 24, BGL 'error' at FATAL 0 of 345,086) -- severity and the time window now filter inside every ranked branch (`db/query.py`, live tests in `test_openstack_live.py` / `test_bgl_live.py`).

**Search windows on the in-place index (`otel_slice`) are untested live.** The window and `total_matches` count there are covered by SQL-shape tests only (`test_search_window.py`): the index was not built during development. Its timestamp is re-read from object storage per candidate row, so a windowed search there may be slow; run `RUN_OTEL_LIVE=1` against a built index before relying on it.

**Pending (not built):** the hypothesis-test tools the brief still requires are
requested from their owner in `docs/tool_requests.md`; T2 and T3 are implemented.

## Setup & commands

- Python 3.14+ and [uv](https://docs.astral.sh/uv/); always run Python through `uv run`, never bare `python`.
- `uv sync` installs deps and the project (editable). `backend` and `ui` are top-level importable from `src/`; run all commands from the repo root (`graph.py` puts its default SQLite checkpointer at `Path.cwd()/.data/checkpoints.sqlite`).
- The shell scripts are NOT executable — run `bash ./backend.sh` / `bash ./frontend.sh` / `bash ./routes.sh`, never `./<name>.sh`.
- `bash ./backend.sh` provisions a demo login user (`uv run python -m backend.appdb.demo`) before starting uvicorn `backend.api:app --reload`. `bash ./frontend.sh` runs `streamlit run src/ui/streamlit_app.py`. Ports come from `.env` (`BACKEND_PORT`/`FRONTEND_PORT`; scripts default 8000/8501 when unset).
- Seed the DB: `bash ./setup.sh` (no arguments) loads both local corpora through the loghub loader (`uv run python -m backend.db.loghub <dataset> --no-embed`): first `openstack` -- one table from `src/backend/data/openstack_abnormal.log`, `openstack_normal1.log`, `openstack_normal2.log` read in that (chronological) order, `LineId` running on across them so its order is time order (207,820 rows) -- then `bgl` from `src/backend/data/BGL.log` (or `BGL_LOG_PATH`; 4.7M rows, slow). `set -e`: a missing source file stops it with the loader's message. Each load drops and rebuilds its table. Needs SereneDB on `localhost:7890` (`postgres`/`postgres`, db `postgres`); no embedding model is needed with `--no-embed`. There is no `backend.db.setup` module and no `TABLE_NAME` constant any more, and the old per-file `openstack_normal1`/`openstack_normal2`/`openstack_abnormal` tables were dropped. `openstack_2k`/`bgl_2k` load loghub's 2,000-line structured CSV samples into the same tables instead.
- Provision a user: `uv run python -m backend.appdb.manage <username> <password>`.
- `LOG_LEVEL=DEBUG bash ./backend.sh` prints tool calls, SQL, and query params.
- `.env` (gitignored) is loaded on import by `src/backend/__init__.py` and `src/ui/__init__.py`; it holds `GROQ_API_KEY`, `DEEPSEEK_API_KEY`, `GOOGLE_API_KEY`, `TYPESAFE_API_KEY`, ports, and auth flags (`AUTH_REGISTRATION_OPEN`, `AUTH_DEMO_*`). `TYPESAFE_API_KEY` is required at import — as are the three model keys, because `models.py` builds its chat clients at import time.
- No lint/format/typecheck/CI is configured (none of ruff/black/mypy/pyright installed). Do not invent those commands.
- `requirements.txt` is **generated**, not hand-edited — it is `uv export` output (the header names the command). Change dependencies in `pyproject.toml` and re-export.
- Line endings: `.gitattributes` sets `* text=auto` and `*.sh eol=lf`. Keep new/edited files LF; untracked files are not normalized by git, so a stray CRLF write persists.
- When scripting against the app, set `CHECKPOINT_BACKEND=memory` (and point `APP_DB_PATH` outside the repo if relevant) so you do not create or mutate `.data/`.

## Pipeline & API notes

- Graph: `normalize -> scope -> (clarify | general | direct_answer | find_evidence) -> answer -> confidence`, with `confidence` looping back to `find_evidence`/`answer`. There is no separate `direct_answer` node — that scope route maps to `answer`. Scope and confidence use atomic TypeSafe Nouls (`decision.py`); code composes their probabilities into policy routes. Scope thresholds are `LOG_REQUEST_THRESHOLD`, `QUERYABLE_SCOPE_THRESHOLD`, `PROCEED_THRESHOLD`, `NEW_EVIDENCE_THRESHOLD`, `FOLLOW_UP_THRESHOLD`, and `MAX_CLARIFY_ROUNDS`; confidence thresholds are `EVIDENCE_REVISION_THRESHOLD` and `ANSWER_OK_THRESHOLD`; per-effort revision budgets live in `effort.py`. Model instances are in `models.py` (Groq `gpt-oss-20b`/`120b`, DeepSeek, Gemini).
- `scope_request` sends the RAW structured `messages` transcript — never `state["normalized"]`, the normalizer's rewrite — plus `latest_message`, `latest_answer`, `mission`, `queryable_targets`, and `tool_catalog`, and asks five Nouls: `is_overview_request` (role-independent; see below), `is_log_request`, `has_queryable_scope`, `proceed_without_clarification`, `needs_new_evidence`. `decide_scope` routes `general` when `is_log_request < LOG_REQUEST_THRESHOLD`; otherwise it clarifies when `has_queryable_scope < QUERYABLE_SCOPE_THRESHOLD` and the user has not authorized proceeding, and otherwise uses `needs_new_evidence` in code to select `direct_answer` or `find_evidence`. **Role is applied only in code:** `decide_scope(response, clarify_count, role)` treats a dataset-wide overview (`is_overview_request >= OVERVIEW_THRESHOLD`) as scoped for `OVERVIEW_ROLES` (team_lead, manager; default scope = whole dataset), while the engineer still needs a target; the Nouls never receive the role. A role-switch run sets `forced_scope` and skips the classifier entirely.
- Clarification and the spent budget (`decision.py`, `graph.scope_node`/`clarify_node`): `scope_node` keeps every turn's raw Noul values (`scope_signals`) next to the code-derived `clarify_reasons` (`decision.clarify_reasons`: which gate failed) and `assumed_scope`. The clarifier gets the same `queryable_context()` (mission, targets, dataset catalog, tool catalog) the scope request is built from, the reasons and `clarify round: n of MAX_CLARIFY_ROUNDS`; from round 2 `clarify_node` makes no model call and returns the fixed `round_two_question()`, whose choices (`clarify_options()`) are built in code from the registry: one per corpus (`Dataset.corpus`; `otel_s3` and `otel_slice` are both "OTel", so users pick a corpus and the agent picks the view) plus "all of them". The model can neither reword the same question nor guess a subset. A spent clarify budget no longer forces `find_evidence`: `needs_new_evidence` still picks `direct_answer`/`find_evidence`; when it investigates without a scope (`decision.scope_assumption`), `assumed_scope` is every local corpus (`datasets.local_datasets()`), the evidence prompt gets an `<assumed scope>` block and `answer_node` prepends the code-rendered `assumed_scope_line`. A turn with no `tool_results` and no `tool_calls` answers in no-evidence mode (`builders.NO_EVIDENCE_RULE` plus only the role's "Question this role asks" and "Never"), so the role's evidence sections are not filled with "nothing".
- `confidence_request` asks independent Nouls about `evidence_relevant`, `evidence_gap_remains`, `gap_closable_by_untried_tool`, `answer_grounded`, `answer_fits_role`, `answer_complete`, and `worth_follow_up`. `decide_confidence` owns the revision route and reason in code, preserving the raw signals in state; Noul probabilities are not separate confidence values.
- `decision.py` builds `TypeSafeClassifier()` at import with no model argument, so the SDK default selects the release; the gate thresholds were live-tuned against whatever it resolved to at the time, so a model release can move them — so importing `backend.pipeline.decision` (or `backend.api`) needs `TYPESAFE_API_KEY`. `decision.py` uses `effort.py`'s `max_iterations` (the confidence revision-loop cap); the old per-effort confidence-threshold field no longer exists.
- HTTP surface is broader than `/chat/stream`: background investigation jobs (`POST /chats/{id}/investigate`, poll `GET /chats/{id}/run/{run_id}`, plus `active-run`/`cancel`) backed by `backend/jobs.py`, plus `/chat/reframe`, auth, chat CRUD, and `/healthz`/`/readyz`/`/metrics`. `/chat/test` returns canned NDJSON for tests.
- `/chat/stream` emits NDJSON events (`messages`, `tool_results`, `tool_progress`, `subgraph_name`, `subgraph_message`). Answers use `[[RESULT:Rn]]` markers serialized by `pipeline/answers.py` and rendered by `ui/rendering.py`; the serializer and renderer must stay in sync with the `id` fields on tool results.
- One reducer folds those events into `{answer, tool_results, progress}`: `src/stream_events` (stdlib only, imports neither `backend` nor `ui`). `backend/jobs.py` uses it with `persist=True` for the progress it saves (shown after the run and on reload) and `ui/main_page.py` with `persist=False` for the live panel; the only intended difference is reasoning (live `thinking_delta` streaming vs the stored consolidated `subgraph_message`). Add a new `tool_progress` status there, never in one layer: the copies once drifted and refusals were saved as failures (`tests/test_stream_events.py`).
- DB query functions return `(sql.Composable, params)` and are wrapped by `query_runner`; each query sets `sdb_ai_allow_insecure_endpoint = true`. Every builder takes a `dataset` id resolved through `db/datasets.py` and composes SQL from canonical fields (`ts`, `severity`, `service`, `message`, `entity_id`, `template`, `record_id`, and `request_id` where declared) -- tool arguments `category`/`service` map to the `Level`/`Component` columns on both local corpora. Every pooled and probe connection runs `SET TimeZone = 'UTC'` (`connection.set_session_time_zone`), so naive window bounds mean UTC everywhere.
- Loaders live in `db/loghub.py`: one `LoghubSpec` per corpus (`bgl`, `bgl_2k`, `openstack`, `openstack_2k`) with its own `line_parser` (`parse_bgl_line` locates fields by the `Level`/`Type` vocabulary; `parse_openstack_line` is a positional regex with a bracketed `ADDR`), `raw_names` (several files share one table with a running `LineId`), and per-spec `header_renames` (only `bgl_2k` renames its CSV `Timestamp`/`Time` headers). `EventTemplate` is derived at load; there is no event id, pid text mirror or per-row embedding.
- Auto-complete selectors are `@` service, `^` template, `$` message text; `!` is only the case-sensitivity modifier after a selector. The only public lookup is `db.auto_complete(query)`, used by `/auto-complete` (no `dataset` parameter; always in-process -- the MCP service has no auto-complete tool): it runs the private per-corpus `_auto_complete_dataset` over the local `.log` corpora (`openstack`, `bgl`), merges the results and tags `$` suggestions with `dataset`; the chat box inserts `Line ID: n (dataset)`.
- `find_evidence` is a **single deep agent** (`create_deep_agent`, deepagents) that calls the thirteen DB tools itself (`list_datasets_tool`, `count_by_dataset_tool`, eight bounded query tools including `get_nearby_events_tool`, plus `sweep_chunks_tool`/`investigate_chunk_tool`) — there is no subagent and no `task` tool (the deepseek harness profile in `agents/find_evidence.py` disables the auto-added general-purpose subagent). It keeps `read_file` (how the skill text is disclosed) and `write_todos`; `_EXCLUDED_TOOLS` strips `write_file`, `edit_file`, `delete`, `execute`, `glob`, `grep`, `ls` from the model request.
- The evidence agent's **state channels depend on the transport**, so tests that
  assert the exact set must branch on `get_db_tools()[1]` (`mcp_enabled`), not on
  `TOOLS_TRANSPORT`: that env var says `mcp` even when the service is unreachable
  and the registry has fallen back to local tools. Local transport passes a
  disk-backed `FilesystemBackend` rooted at `skills/`, giving
  `{messages, structured_response, todos}`. Under MCP the skill text comes from
  the `list_skills`/`read_skill` tools, no backend is passed, and deepagents
  installs its default **state-backed** store, which adds an (unused) `files`
  channel. The transport-independent invariant is that no channel carries the
  report -- it is built off-agent. See the two tests at the end of
  `tests/test_find_evidence.py`.
- `skills/` at the repo root is **mandatory** — `agents/find_evidence.py` raises at import if it is missing — and it is the `FilesystemBackend` root, so `read_file` cannot reach anything else in the repo. This is NOT `.agents/skills/` (an unrelated local skills dir); the pipeline loads the repo-root `skills/`.
- The evidence report is built in two parts. **Code** builds the evidence items (`pipeline/evidence.py::build_evidence`): one item per database-tool call from `tools/results.py::collect_tool_calls`, ids `E1..En` in call order, with the exact tool name, arguments, `success`/`failure` status, error text and linked `R`-ids; `availability` is `available` only when the call produced a record, so failed, empty and limit-exceeded calls show as `unavailable`. The **model** writes only the judgement (`agents/evidence_report.py::generate_evidence_judgement` -> `contracts.EvidenceJudgement`: `summary` and at most 3 `hypotheses` citing the listed `E`-ids). `graph.find_evidence_node` assembles `EvidenceReport(summary, evidence, hypotheses, data_scope)`, so its shape and every reader (answer prompt, confidence prompt, `worked_investigation.py`, stored history) are unchanged.
- The judgement call is a plain `deepseek.invoke(messages)` (**no** `response_format`) validated locally with `EvidenceJudgement.model_validate_json(message.text)`. The structured-output guarantee is deliberately omitted: in any form (`with_structured_output(..., method="json_mode")`, `.bind(response_format=...)`, or an `invoke(..., response_format=...)` kwarg) `response_format` collapses the streamed reply to exactly one delta, so the model's reasoning could not render token-by-token in the live progress panel. `generate_normalized` (`agents/normalize.py`) and `generate_answer` (`agents/answer.py`) follow the same pattern. Because no schema is transmitted, the JSON contract must ride in the prompt text (`JSON_OUTPUT_SPEC`) and every closed vocabulary must be enumerated there (hypothesis `status` is exactly `supported`, `unsupported` or `inconclusive`; at most 3 hypotheses). (`AIMessage.text` is the text blocks only, so the reasoning blocks are excluded from the parsed payload.)
- The judgement path is **guard-free**: no `try`/`except`, no empty fallback, no citation filtering, no re-validation. A provider failure or contract violation (for example 4 hypotheses) propagates out of `find_evidence_node`; `api.py::chat_stream` is `try`/`finally` with no `except`, so it tears the NDJSON stream, while background investigations record `status=error`. Switch to fixing violations in code only if live runs keep hitting them.
- Tool results: `tools/results.py::collect_tool_results` reads the agent's own messages and assigns `id` (`R{n}`), `tool_call_id` and `row_count` inline, so those records ARE the display contract `{id, tool_name, arguments, row_count, rows}` consumed by `answers.py` (`valid_ids`), `api.py` and `ui/rendering.py`. `rows` is capped at `MAX_RESULT_ROWS = 100` (the largest tool cap) for display; the tools themselves return full row sets into the agent's context. `collect_tool_calls` lists every database-tool call (also failed and empty ones) and feeds the evidence items and the confidence input `attempted_tools` (`builders.summarized_attempts(tool_results, tool_calls)`), so a failed or empty call is visible to the "can an untried tool close the gap?" question; the state key is `tool_calls`.
- Answer prompt catalog (`builders.build_result_catalog`): measured results (`aggregate`, `trend`, `derived`) show every row up to `ANSWER_MEASURED_ROWS = 100`; examples (`search`, `lookup`, ...) show `ANSWER_EXAMPLE_ROWS = 10`, while context results show up to `ANSWER_CONTEXT_ROWS = 40` nearest the anchor; each result states rows returned versus rows included in the prompt. Over `ANSWER_CATALOG_CHAR_BUDGET` (120,000 chars) example rows shrink to 1, newest first; measured rows are never cut — if they alone exceed the budget a warning is logged and a `Note:` goes into the data-scope appendix. `answer_node` logs the prompt size and `generate_answer` the provider token usage (live run at High effort: 15-22k chars, 6.2-8.9k input tokens, far under the budget). The constants are starting values, not tuned.
- Role answer rules live only in the role skills (`## Question this role asks`, `## Answer must contain`, `## Never`); `playbooks.role_answer_rules(role)` extracts them for the answer prompt and raises `ValueError` on a missing section. There is no second copy in code.
- Answer assembly (`pipeline/answers.py`): the model returns narrative `blocks` plus typed `findings` (measured / hypothesis / limitation, cited to R-ids) and `recommendations`; **code** renders the labelled ledger, the "Recommended next steps" and the "Data scope and queries" appendix (datasets, windows, filters, measured vs example results, truncation, executed SQL per R-id). A `measured` finding with no valid R-id is downgraded to a hypothesis. `api._context_text` strips the appendix (`strip_appendix`) before an answer is fed back to the classifiers as conversation context. For team lead and manager, `graph.answer_node` adds a derived `priority_score` record (`pipeline/priority.py`, formula shown in the answer), computed in code from the measured counts.
- Role switch: the UI's per-answer role buttons call `POST /chats/{id}/messages/{seq}/role-answer`, which runs a NEW investigation for the target role (own graph thread, own `jobs` slot, `forced_scope`) and caches it in the app DB `role_answers` table keyed by (message, role); a request at the same or lower effort is a cache hit, a higher effort re-runs. `/chat/reframe` still exists for compatibility but the UI no longer uses it (a reframe reuses the other role's evidence, which the brief rules out).
- Budgets: `effort.py` sets ONE all-tools `ToolCallLimitMiddleware(run_limit)` per effort — Low 6, Medium 10, High 12, Extreme 18, Brutal 22 — and to-do writes count against it. `max_iterations` remains the confidence revision-loop cap.
- Tool progress reaches the UI only from depth ≤ 1. The DB tools emit `tool_progress` payloads on the graph's custom stream from inside the tool (`tools/executor.py`), and failures are re-raised as a generic `RuntimeError` so `handle_tool_errors` can convert them into a ToolMessage. The API's projection captures the root `custom` scope plus ONE level of direct-child `custom` only, so an event emitted from a deeper namespace never reaches the UI. Keep tool calls on the main agent for this reason.

### MCP tool service

`mcp_server.sh` runs the standalone FastMCP Streamable HTTP service on
`127.0.0.1:8010/mcp` (`python -m backend.mcp_server --transport stdio` for a client
that launches it). The pipeline defaults to local tools; set `TOOLS_TRANSPORT=mcp`
to use the server for the thirteen DB tools and skills. `/auto-complete` is not on
the server: it always runs in-process. The synchronous pipeline uses a dedicated
asyncio loop thread for MCP calls and falls back to local DB tools when the service
is unavailable.

The server (`src/backend/mcp_server/`) is assembled from the same sources as the
pipeline and holds no text of its own: tools from the spec table (`tools.py`),
guidance rendered from `roles.py`/`envelope.py`/`builders.py` (`instructions.py`),
role prompts from `builders.evidence_brief` + `answers.answer_layout`
(`prompts.py`), resources from the dataset registry, role/effort tables, priority
formula and ownership CSV (`resources.py`; skills via FastMCP's
`SkillsDirectoryProvider`, URIs `skill://<name>/SKILL.md`). It must import without
the chatbot's model keys (do not import `pipeline.models`, `decision`, `graph` or
`api`; a test checks). `fastmcp` is pinned in `pyproject.toml`, and
`requirements.txt` must be regenerated with `uv export`, not edited manually. Under
FastMCP 4 decorators return the plain function; run MCP tests with
`FASTMCP_MCP_CAMELCASE_COMPAT=false` to catch deprecated camelCase field reads.
Auth is `MCP_AUTH_TOKEN` through a `TokenVerifier` (constant-time compare); the HTTP
app turns on the Host/Origin guard; loopback needs no token, a non-loopback bind
requires one. Size limits (`MAX_CELL_CHARS`, `MAX_RESULT_CHARS`) live in
`envelope.build_envelope`, so both transports clip identically. The plan and its
status are in `docs/mcp_server_plan.md`.
